## 腾讯云轻量服务器部署可行性评估

用户提出要把项目部署到腾讯云轻量应用服务器（lhins-kjsnc8ht / 134.175.156.233，广州，2C2G / 50GB SSD / 4Mbps）。

### 评估结论

资源层面可行（PRD §55 本就是单机低并发设计，内存约 1.0GB / 2GB），但**安全层面当前状态不可上公网**，识别出 4 个 P0 阻断项：

1. **P0-1 实例 5 天后到期**（2026-10-04 08:40），到期进回收期约 7 天后释放、数据不可找回。必须先续费。
2. **P0-2 全链路无 TLS**。全仓搜索无任何 TLS/证书配置，所有 nginx 只监听 80。登录密码、会话 Cookie、科应账号密码明文过公网。且 `main.ts` 的 CORS 默认白名单放行 `chrome-extension://`，裸 IP 部署下任何装该扩展的人都能跨域调 API。需域名 + Let's Encrypt + `CORS_ORIGINS` 收敛。
3. **P0-3 3000 端口直连公网**。`docker-compose.rancher.yml` 里 `ports: "3000:3000"` 绑 0.0.0.0，绕过 nginx，且 `trust proxy: 'loopback'` 下真实客户端 IP 可被伪造头污染，限流键可绕过。
4. **P0-4 备份仅存本机盘**。备份与 SQLite 同盘，实例释放即全丢；`SCIENCEING_MASTER_KEY` 若只在服务器 `.env` 上，丢失后已入库科应密码永久不可解密。

### 关键架构事实（本次摸清）

- Worker 由后端 `spawn(process.execPath, [cli, ...])` 拉起为**子进程**（`apps/server/src/modules/automation/worker-client.ts:142`），因此 Chromium 必须与后端同容器/同主机。
- `docker-compose.rancher.yml` **缺 Worker 服务**，只有 backend + gateway，照抄会导致自动改密不可用。
- 现有发布链路（`deploy-prod.bat` / `deploy-release.ps1` / `sync-from-dev.ps1`）是 PowerShell + SMB + `D:\scienceing-prod`，**Linux 上完全不可用**。建议：Windows 开发机构建 Release → 打 Docker 镜像 → 服务器 compose 部署。
- Chromium 容器内需 `--no-sandbox` + `shm_size ≥ 512MB`（默认 64MB 会崩）。
- nginx `add_header` 不继承，子 location 写了自己的 `add_header` 会让父级 CSP 等全部失效，已有回归测试 `scripts/test/security-headers.test.mjs` 覆盖。

## 云部署方案设计（第二轮，用户要求「不考虑到期，完全解决」）

### 新增关键发现（比第一轮更关键，都在容器化场景才暴露）

1. **容器化会让登录限流彻底失效。** `main.ts:54` 硬编码 `trust proxy = 'loopback'`，但 Docker 下 nginx 在网桥（172.28.x）而非回环，Express 不采信 XFF → `req.ip` 退化成 nginx 容器 IP → `clientKey()` 所有用户同一个键 → **任意 10 次失败登录锁死全团队 15 分钟**。这是本方案唯一必须改的源码，已在设计文档给出 diff（默认值保持 `loopback`，开发/LAN 零影响）。
2. **unpacked 扩展的 ID 由扩展目录绝对路径派生**，每人解压路径不同 → ID 不同。所以「把 CORS 收敛到具体扩展 ID」的前置条件是**先在 manifest.json 注入 `key`（RSA 公钥）固定 ID**。已实现于 `patch-extension.mjs`。
3. **`CORS_ORIGINS` 一旦非空会整体替换默认白名单**（`main.ts:32`），替换后必须手动补回 `chrome-extension://<ID>`，否则扩展 service worker 被 CORS 拦死。已写进 `.env.example` 注释。
4. Worker 代码里**已经有** `--no-sandbox` 和 `--disable-dev-shm-usage`（`cli.ts:95`、`worker.ts:52`），且 `SCIENCING_BROWSER_CHANNEL` 支持 `chromium`（`config.ts:106`）。所以容器化不需要装 Google Chrome，用 Playwright 官方镜像即可。第一轮评估里「需要 --no-sandbox」的说法是多余的。
5. `GET /api/extension/config`（`extension.controller.ts:64`）**无 AuthGuard**，是现成的公开探针，健康检查直接用，不必新开接口。
6. 首次签证书有引导死锁（证书没有 → nginx 起不来 → ACME 要 80 端口）。解法：停 gateway 让出 80 → certbot `--standalone` 签发 → 再拉起。

### 方案要点

- 两段网络：`edge`（仅 gateway，暴露 80/443）+ `internal`（172.28.0.0/16，app 不 publish 任何端口）。
- 单容器装后端 + Worker（Worker 是 `spawn` 出来的子进程，拆容器会找不到 CLI）。
- 基础镜像 `mcr.microsoft.com/playwright:v1.49.0-jammy`，零安装零编译（build context 就是 Release 解压目录）。
- 安全头抽成 snippet，规避 nginx `add_header` 不继承的坑。
- 备份异地化：容器内 `VACUUM INTO` → 校验关键表非空 → rclone 到 COS。

## 访问方式决策：路线 B（IP + IP 证书）——第三轮

### 关键约束：ICP 备案（推翻了我第一轮的方案前提）

第一轮我建议「注册域名 + Let's Encrypt」，但**漏了 ICP 备案这一环**。腾讯云官方文档明确：使用中国内地地域轻量服务器**开办网站并绑定域名服务时必须先办理 ICP 备案**，取得备案号后才能开通域名访问（国务院令第292号）。

备案硬性前置条件，本项目一条都不满足：
- 实例需**包年包月且购买时长 ≥ 90 天**（当前仅 1 个月）
- **备案期间剩余时长 ≥ 30 天**（当前剩 5 天）
- 域名须境内注册商 + 已实名认证 + 主体信息一致
- 叠加首次备案 1–3 周管局审核 → 整体 2–4 周外部等待

注意：这不是「到期会丢数据」的问题，而是「不续费就永远拿不到备案号」。即使用户说「不考虑到期」，这个约束也绕不开。

### 解法：Let's Encrypt IP 地址证书（2026-01-15 GA）

- 裸 IP 可取得浏览器信任的证书，**不需要域名、不需要备案**
- 硬性要求：必须是 `shortlived` profile，**有效期 160 小时（约 6.7 天）**
- Certbot ≥ 5.4（`--ip-address` + webroot）、≥ 4.0（`--preferred-profile`）；当前最新 5.8.0
- Certbot **只支持签发、不支持自动装进 web server**，需手工配 nginx 证书路径
- 命令：`certbot certonly --standalone --preferred-profile shortlived --ip-address <IP>`

**代价**：6 天有效期 → 续期必须每天一次且全自动，cron 停摆 6 天内服务即断；访问地址是 IP，IP 变更则证书/扩展/CORS 全部失效。

### 修掉一个真实缺陷：脚本 `source .env` 会被特殊字符破坏

三个脚本（issue-cert / renew-cert / verify-deploy）原本用 `set -a; . ./.env; set +a` 读取配置。**实测复现**：`.env` 里 `PASSWORD=abc$def\`whoami\`` source 后变成 `abclizhicai` —— 变量被展开、**反引号里的命令被真实执行**。生产 `.env` 存的正是管理员口令这类任意字符，这个 bug 会静默改坏口令甚至导致命令注入。

改为 `env_get() { sed -n "s/^$1=//p" .env | head -1 | tr -d '\r'; }` 按需提取单个键，原样读取不解析。已验证 `abc$def\`whoami\`xyz` 原样读出。

**这是个可复用的经验**：任何脚本读 `.env` 都不该 source，尤其当值可能含 `$`、反引号、空格时。

## 第五轮：密码安全审计（用户明确要求「审查部署到公网后不会有任何密码风险」）

### 审计范围

覆盖五类凭据：员工登录密码、科应账号密码、科应管理员凭据、会话/租约令牌、扩展一次性证明。阅读了全部 crypto 模块、全部密码相关 service、守卫、前端/扩展/Worker 代码、审计日志、脱敏函数、限流器。

### 发现与修复

**登录时序侧信道（已修复）**：`auth.service.ts` 中用户不存在时直接抛 401（~0 ms），用户存在时执行 `bcrypt.compare`（~77 ms），时序差可被用于账号枚举。**修复**：在 `!row` 分支也执行一次 `verifyPassword(password, DUMMY_HASH)`，时序差降至 < 2 ms（实测 1.1 ms）。改动文件：`apps/server/src/crypto/password.ts`（新增 `DUMMY_HASH` 常量）、`apps/server/src/modules/auth/auth.service.ts`（`login` 方法）。

### 审计结论

除已修复的时序侧信道外，五类凭据的存储、传输、日志暴露链路均未发现密码泄漏或被攻击者直接利用的漏洞。具体结论：

- 员工登录密码：bcryptjs 10 rounds，只存 hash —— ✅ 安全
- 科应账号密码：AES-256-GCM + AAD 绑定账号 id，v1→v2 平滑迁移 —— ✅ 安全
- 科应管理员凭据：仅环境变量，不入库/镜像/Git —— ✅ 安全（邮箱固定为 `lishenggao@highpowertech.com`，密码必须与开发环境不同）
- 会话 token：只存 SHA-256 哈希，Cookie HttpOnly+Secure+SameSite=Lax —— ✅ 安全
- leaseToken：只存 SHA-256 哈希，1 分钟 TTL，消费即作废 —— ✅ 安全
- 扩展一次性证明：只存 SHA-256 哈希，30 秒 TTL —— ✅ 安全

### 残余风险（P1/P2，非阻断）

- 进程内限流（单实例可接受，多实例需改 Redis）
- 扩展消息未校验 origin（生产仅一域名 + matches 限制，可控）
- IP 证书 6 天有效期（自动续期已配置 cron，失效则浏览器阻断访问，非密码泄漏风险）
